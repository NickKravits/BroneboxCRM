# Bronebox CRM

Фронтенд (веб-интерфейс) платформы **Bronebox** — сервиса для управления бизнесом посуточной аренды квартир. Работает поверх бэкенда **[BroneboxAPI](https://github.com/NickKravits/BroneboxAPI)**.

Это часть проекта из двух репозиториев:
- **[BroneboxAPI](https://github.com/NickKravits/BroneboxAPI)** — бэкенд (REST API)
- **BroneboxCRM** (этот репозиторий) — фронтенд

## О проекте

CRM-панель для владельцев/администраторов бизнеса посуточной аренды: бронирования, объекты, горничные и график уборки, финансы, чаты с гостями, заметки, журнал действий, настройки кабинета. Отдельно — публичные гостевые страницы (оплата, договор, отзыв) для людей, снимающих жильё.

Сделано на чистом HTML/CSS/JavaScript, без фреймворков и сборщика — это статические файлы, которые может отдавать любой веб-сервер.

## Стек

- Vanilla JavaScript (без фреймворков и без сборки)
- HTML5 / CSS3
- [DOMPurify](https://github.com/cure53/DOMPurify) (санитизация пользовательского контента, подключается с CDN)
- Обмен данными с [BroneboxAPI](https://github.com/NickKravits/BroneboxAPI) через `fetch`

## Требования

- Любой статический веб-сервер (nginx, Apache, `http-server`, VS Code Live Server и т.п.)
- Запущенный и доступный [BroneboxAPI](https://github.com/NickKravits/BroneboxAPI)

## Установка и запуск

**1. Клонировать репозиторий**

```bash
git clone https://github.com/NickKravits/BroneboxCRM.git
cd BroneboxCRM
```

**2. Указать адрес API в `config.js`**

```js
const API   = 'http://127.0.0.1:3000'   // адрес запущенного BroneboxAPI
const DOMEN = 'http://127.0.0.1:5500'   // адрес, на котором крутится сам фронтенд
```

> Проект без сборщика и не читает `.env` в браузере — файл `.env.example` служит справочником (переменные `IP_ADDRESS` и `DOMEN`), значения из него нужно вручную перенести в `config.js`.

**3. Запустить статический сервер в корне репозитория**

Например:

```bash
npx http-server . -p 5500
```

...или через расширение **Live Server** в VS Code (по умолчанию проект рассчитан на порт `5500`, как в `config.js`).

**4. Открыть в браузере**

```
http://127.0.0.1:5500/login/
```

После входа откроется панель `/crm/`.

## Маршрутизация

Папка `c/` содержит `.htaccess` с правилом переписывания вида `/c/{id}` → `c/index.html` — это публичная страница бронирования для гостя. Если хостинг не на Apache (nginx, Vercel, Netlify и т.п.), аналогичное правило rewrite нужно настроить в конфигурации сервера отдельно.

## Обновление статики у пользователей после деплоя

Все `styles.css`/`app-shell.css`/`app-shell.js` подключаются с `?v=<git-хэш>` — при каждом деплое хэш меняется, и браузер каждого пользователя гарантированно скачивает свежие файлы вместо кэша, без каких-либо действий с их стороны. Версию проставляет `bump-version.sh`; параллельно он пишет `crm/version.json`, который на лету опрашивает баннер обновления в приложении — если у кого-то открыта старая вкладка/WebApp, ему предложат обновиться, даже если обычная перезагрузка страницы у него не помогает (актуально для установленных на iOS WebApp).

**На сервере деплой делайте через `bash deploy.sh`, а не голым `git pull`.** Он сбрасывает предыдущий локальный бамп версии перед тем, как тянуть новые коммиты, поэтому не возникает конфликта на строках `?v=...` (если версия менялась и локально, и в новых коммитах — голый `git pull` может на этом споткнуться).

Разовая настройка на сервере:

```bash
chmod +x deploy.sh bump-version.sh .githooks/post-merge
```

Дальше просто: `bash deploy.sh`.

(Хук `.githooks/post-merge` тоже подключён на случай, если кто-то по привычке всё же вызовет `git pull` напрямую — версия обновится и тогда, просто без гарантии от конфликта, которую даёт `deploy.sh`.)

> Важно: эта схема работает, только если сами HTML-файлы (`index.html`) не кэшируются браузером надолго — иначе он не увидит новый `?v=...` в разметке. Обычно так и есть по умолчанию, но если на сервере настроен долгий `Cache-Control` для `.html`, это стоит проверить в конфигурации nginx/веб-сервера отдельно.
